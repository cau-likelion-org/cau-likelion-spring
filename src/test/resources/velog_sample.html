Next.js를 쓰다 보면 한 번쯤 이런 생각이 든다.
"HTML이 이미 완성돼서 오네?" 🫢

그게 바로 SSR(Server Side Rendering)의 특징이다.
서버에서 데이터를 미리 준비해서, 빈 화면이 아니라 꽉 찬 HTML을 보내준다. 덕분에 사용자는 로딩 없이 빠르게 화면을 볼 수 있고, 검색 엔진(SEO)도 콘텐츠를 온전히 읽을 수 있다.

그런데 여기서 문제 하나.... 🤔

👉 "React Query는 클라이언트에서 쓰는 거 아니야?"

React Query는 기본적으로 브라우저(Client)에서 데이터를 페칭하고 관리하는 데 특화되어 있기 때문에 이걸 서버(Next.js) 환경에서 '제대로' 쓰려면 중간에 한 가지 연결 고리가 필요하다.

그게 바로 오늘 알아볼 Hydration 패턴이다.

1. 왜 SSR 환경에서 TanStack Query가 까다로울까?

React Query는 기본적으로 클라이언트 캐시를 기반으로 동작하는 CSR(Client Side Rendering) 라이브러리이다. 이 특성 때문에 Next.js와 같은 SSR 환경에서 그대로 사용할 경우 다음과 같은 문제가 발생한다.

  1. 데이터 불일치
    서버에서 이미 데이터를 가져와 HTML을 생성했음에도, 클라이언트에서 다시 loading 상태가 발생하며 데이터를 재요청하게 된다. 이는 SSR의 장점인 빠른 초기 렌더링을 저해한다.

  2. 직렬화(Serialization) 문제
    서버의 Query Cache는 복잡한 객체 구조이기 때문에, 이를 클라이언트로 전달하기 위해서는 JSON 형태로 직렬화하는 과정이 필요하다.

이러한 문제의 근본 원인은 서버에서 생성된 데이터와 클라이언트의 QueryClient 캐시가 서로 분리되어 있기 때문이다.

💡 이 문제를 해결하는 방법이 바로 Hydration 패턴이다.
Hydration은 서버에서 생성된 캐시 상태를 클라이언트로 전달하고, 이를 다시 복원하여 서버와 클라이언트가 동일한 상태를 공유하도록 만든다.

2. Dehydration & Hydration

가장 중요한 포인트는 데이터가 아니라 캐시(QueryClient)의 상태를 통째로 옮기는 것인데 이는 단순한 데이터 전달이 아닌 서버와 클라이언트가 동일한 상태를 공유하도록 만드는 과정이다

🔹 Dehydration (탈수)

서버에서 prefetch된 Query Cache를 클라이언트로 전달할 수 있도록 JSON 형태로 직렬화하는 과정

const dehydratedState = dehydrate(queryClient);
  • QueryClient 내부 캐시를 “이동 가능한 형태”로 변환한다
  • 서버 메모리에 있는 상태를 클라이언트로 넘기기 위한 준비 단계

🔹 Hydration (수분 공급)

서버에서 전달된 JSON 데이터를 클라이언트의 QueryClient 캐시에 다시 주입하는 과정

<HydrationBoundary state={dehydratedState}>
  <App />
</HydrationBoundary>
  • 서버에서 만든 캐시 상태를 그대로 복원한다
  • 클라이언트에서도 서버와 동일한 cache를 사용하게 된다

이 과정을 통해 다음과 같은 이점을 얻을 수 있다

  1. 중복 요청 방지: 서버에서 가져온 데이터를 클라이언트에서 다시 요청하지 않는다
  2. Zero-Loading: 초기 렌더링 시 loading 없이 즉시 데이터를 사용할 수 있다

결론적으로 SSR의 빠른 초기 렌더링과 React Query의 캐싱 전략을 동시에 활용할 수 있게 되는 것! 🚀

3. 구현 (Next.js App Router 기준)

이제 실제로 서버 → 클라이언트로 상태를 넘기는 전체 흐름을 구현해보자

🛠️ 전체 흐름

  1. 서버에서 QueryClient 생성
  2. 데이터 prefetch
  3. 캐시를 dehydrate
  4. 클라이언트에서 hydrate
  5. useQuery로 캐시 데이터 그대로 사용

① QueryClient 싱글톤 설정 (클라이언트)

클라이언트에서는 QueryClient를 싱글톤으로 유지해야 페이지를 이동해도 캐시가 날아가지 않고 유지된다

// app/providers.tsx
'use client'

import { QueryClient, QueryClientProvider } from '@tanstack/react-query'
import { useState } from 'react'

export default function Providers({ children }: { children: React.ReactNode }) {
  const [queryClient] = useState(
    () =>
      new QueryClient({
        defaultOptions: {
          queries: {
            // 서버와 클라이언트 간 데이터 재요청을 줄이기 위한 핵심 설정
            staleTime: 60 * 1000,
          },
        },
      })
  )

  return (
    <QueryClientProvider client={queryClient}>
      {children}
    </QueryClientProvider>
  )
}
  • 클라이언트는 한 번 만든 캐시를 계속 재사용한다
  • 주의: staleTime이 없으면 hydration 직후 클라이언트에서 바로 refetch가 발생할 수 있다

② 서버 컴포넌트에서 Prefetch + Dehydrate

서버에서는 요청마다 새로운 QueryClient를 생성하고, 데이터를 "미리 준비"한다

// app/book/[id]/page.tsx
import { dehydrate, HydrationBoundary, QueryClient } from '@tanstack/react-query'
import BookDetail from '@/components/BookDetail'

export default async function Page({ params: { id } }: { params: { id: string } }) {
  const queryClient = new QueryClient()

  // 1. 서버에서 데이터 prefetch
  await queryClient.prefetchQuery({
    queryKey: ['book', id],
    queryFn: () => fetchBookById(id),
  })

  return (
    // 2. 캐시 상태를 압축(dehydrate)해서 클라이언트로 전달
    <HydrationBoundary state={dehydrate(queryClient)}>
      <BookDetail id={id} />
    </HydrationBoundary>
  )
}
  • 서버는 데이터 Fetching을 담당하고, 클라이언트는 그 결과를 그대로 재사용하게 된다

③ 클라이언트 컴포넌트에서 useQuery

클라이언트에서는 아무 일도 없었던 것처럼 useQuery를 사용하는데 이미 캐시가 채워져 있기 때문에 로딩 없이 즉시 렌더링된다

// components/BookDetail.tsx
'use client'

import { useQuery } from '@tanstack/react-query'

export default function BookDetail({ id }: { id: string }) {
  const { data } = useQuery({
    queryKey: ['book', id],
    queryFn: () => fetchBookById(id),
  })

  return (
    <div>
      <h1>{data?.title}</h1>
      <p>{data?.description}</p>
    </div>
  )
}
  • isLoading 없이 바로 데이터 사용이 가능하다
  • 주의: queryKey가 서버의 prefetchQuery와 반드시 동일해야 한다!

🔥 전체 흐름 요약

  1. [서버] prefetchQuery → 캐시(Cache) 생성
  2. [서버] dehydrate → 데이터를 JSON으로 압축 변환
  3. [클라이언트] hydrate → 압축된 데이터를 캐시로 복원
  4. [클라이언트] useQuery → 네트워크 요청 없이 즉시 데이터 사용

"서버에서 데이터를 미리 준비하고, 클라이언트는 그걸 그대로 이어받는다!" 🤝

4. 왜 이 방식을 선택했는가?

🚀 압도적인 사용자 경험 (UX)

사용자가 링크를 클릭하자마자 '로딩 중...' 화면 없이 완성된 페이지를 보게 되기 때문에 CSR 대비 압도적인 TTV(Time to View)를 가진다.

🔍 강력한 SEO

Next.js의 핵심 가치인 "데이터가 채워진 HTML을 초기 렌더링에서 제공하는 것"을 만족시킨다. CSR의 유연함을 유지하면서도 SEO를 함께 고려할 수 있는 최고의 합의점 아닐까?

🛠️ Props Drilling 해방

기존에는 서버에서 받은 데이터를 하위 컴포넌트로 전달하기 위해 Props를 계속 내려줘야 했지만
이 방식을 사용하면 queryKey만 일치하면 어느 컴포넌트에서든 캐시에 직접 접근할 수 있다.

💎 데이터 무결성

여러 컴포넌트가 동일한 데이터를 필요로 할 때, 공유된 Query Cache를 기반으로 동일한 데이터를 참조하게 된다. 이로 인해 중복 요청 없이 데이터가 한 곳에서 관리되며, 애플리케이션 전반에서 데이터의 무결성과 동기성이 자연스럽게 유지된다.

5. 서버가 관리하는 것은 결과가 아닌 '상태'

React Query는 SSR 환경에서 단순히 API 결과값(JSON)만 전달하는 도구가 아니다.
핵심은 서버의 Query Cache 상태 자체를 클라이언트로 전달한다는 점에 있다.

1. 관심사의 분리

개발자는 '이 데이터를 어디에서 가져올지'를 고민하기보다, 동일한 queryKey를 기준으로 '어떤 데이터를 어떻게 보여줄지'에 집중할 수 있다.

2. 상태 기반 데이터 흐름

서버에서 prefetch된 데이터는 클라이언트에서 hydrate되며, 즉시 사용할 수 있는 캐시 상태로 복원되는데 이 상태는 이후의 백그라운드 refetch, 캐시 무효화 등 React Query의 모든 데이터 관리 흐름에 자연스럽게 연결된다.

🚀 결국 Hydration 패턴은

단순히 초기 렌더링 속도를 개선하는 것을 넘어, 서버와 클라이언트가 동일한 상태를 공유하도록 만드는 방식이라고 할 수 있다. 이제 더 이상 서버냐 클라이언트냐 고민할 필요 없다.

그냥… 같은 상태를 쓰면 된다 😎
